# 고정 RX 2.0.1-rx-b64: 실기기 복구 배포물

2026-11-17 연결된 ESP32-S3 RX의 플래시에서 읽어 복구한 이미지입니다.
코드를 수정하거나 버전 문자열만 바꿔 만든 이미지가 아닙니다.
앱은 2026-10-15 18:50:13 / ESP-IDF v6.0.1 빌드이며,
10월 15·19일 수집 로그에서 관측된 ELF 식별 접두사 `f4ac3fec6`과 같습니다.

**원본 2.0.1 소스와 ELF 파일은 미확보 상태입니다.** 저장소의 `csi_recv/`는
2.0.0 소스이며 이 이미지와 일치한다고 주장하지 않습니다. 내부 처리·gain 보정·
패킷 파서가 2.0.0과 정확히 어떻게 다른지는 소스 확보 전에는 확정할 수 없습니다.

## 확인한 정보

- 앱: `csi_recv`, 버전 `2.0.1-rx-b64`, ESP32-S3.
- 앱 ELF SHA-256: `f4ac3fec62a1bff580d1843c9210bedccf77943ec97ce9f26bd2a808e48db123`.
- 앱 BIN: 754704바이트. 각 파일의 SHA-256은 `SHA256SUMS` 참고.
- 앱과 부트로더의 이미지 체크섬 및 내장 SHA-256 검증 통과.
- 부팅 출력: `CSI_RX_READY,1,2.0.1-rx-b64,32,768` 및 `CSI_CTRL_READY`.
- CSV 헤더: 기존 28필드, 마지막 `data_b64`. UART 921600 baud.
- 부팅은 확인했지만 이번 작업에는 TX 송신·실수신률·손실률·재설치 검증이 없습니다.

현재 보드에는 새 펌웨어를 쓰거나 지우지 않았습니다. 읽기를 위해 재부팅했고,
애플리케이션 설정 변경 명령도 보내지 않았습니다. 복구 시점의 앱·부트로더·
파티션 표를 포함하며 NVS와 보드별 RF 교정 데이터는 배포하지 않습니다.

## 빌드 없이 설치

저장소 전체를 받은 뒤 루트 PowerShell에서 실제 RX 포트를 지정합니다.
이 안내는 고정 RX용이며 TX에는 설치하지 않습니다.

```powershell
python -m pip install 'esptool>=5,<6'
.\scripts\flash-rx-2.0.1.ps1 -Port COM_RX -DryRun
# 설치가 필요한 RX에만 실행:
.\scripts\flash-rx-2.0.1.ps1 -Port COM_RX
```

스크립트는 바이너리 3개의 SHA-256을 확인합니다. `-DryRun`은 포트에 접근하지
않습니다. 기본 설치 보율은 460800이며 오류 시 `-Baud 115200`을 사용합니다.
설치 후 콘솔은 921600 baud / 8N1입니다.

| 오프셋 | 파일 |
| --- | --- |
| `0x0` | `bootloader/bootloader.bin` |
| `0xa000` | `partition_table/partition-table.bin` |
| `0x20000` | `csi_recv.bin` |

DIO/80MHz/2MB 이미지이며 기존 팀 파티션 배치를 사용합니다.
실제 보드는 8MB 플래시로 식별됐습니다. 다른 파티션 배치의 보드에는 기존
플래시/NVS 백업과 호환성을 먼저 확인하세요. 이 패키지는 전체 칩 지우기를 하지 않습니다.

## 복구 이력

`recovery-info.json`에 복구 원본 해시, 앱 ELF 해시, 각 배포 파일 해시와
검증 범위를 기록했습니다. 앱 파티션의 뒤쪽 비이미지 데이터는 제외했고,
부트로더 역시 검증된 이미지 끝까지만 포함합니다. 파티션 표는 읽은 4KB입니다.
`scripts/package-recovered-rx.py`는 로컬 읽기 덤프에서 같은 패키지를 생성하는
도구이며 장치 포트를 열지 않습니다. 개인별 NVS가 포함될 수 있는 전체
플래시 덤프는 GitHub에 올리지 않습니다.

수집기는 `CSI_DATA_B64`를 처리해야 합니다. [기존 인계서](../../COLLECTOR_FORMAT_HANDOFF_KO.md)의
CSV·식별자 설명은 참고하되, 2.0.0 코드의 내부 동작이 2.0.1에서도 같다고
가정하지 마세요. 출력 스키마와 내부 알고리즘의 동일성은 별개의 확인 사항입니다.
